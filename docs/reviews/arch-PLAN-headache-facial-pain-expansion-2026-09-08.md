# Architect review — PR #<fill on open> — headache ICHD-3 facial-pain expansion (13.2 GPN + 13.12 PIFP)

**Date:** 2026-09-08

## Rationale

This is additive work inside an architecture that was already decided (ADR-2026-07-06) and already stress-tested (the 2026-09-07 routing batch), and the plan reaches for the right joints throughout: criteria stay in `clinicHeadacheData.ts`, routing stays in `headacheQuestions.ts`, management prose stays in `HeadacheManagement.tsx`, verbatim text stays in `registry.ts`, and the two new phenotypes are shaped after occipital neuralgia, which is the correct exemplar (a §13 neuralgia with no Probable sub-form, therefore binary full-or-hidden). No new module, no new abstraction, no new dependency, no new state. The plan also correctly anticipates the two hazards that bit last time: it names the sev-very-severe reuse lesson before choosing chips, and it names the BC-6 label-collision class before writing a new location option. That is the right instinct applied at the right moment. Three things are not yet right. First, the plan leaves the branch-shape question open, and the answer materially changes the safety profile: putting GPN and PIFP options on the existing `q-trigeminal` screen creates a concrete false-positive path to a **full** trigeminal-neuralgia match on a glossopharyngeal presentation, because `loc-trigeminal-distribution`'s label says "jaw", `tn-trigger`'s label says "talking", and GPN's own territory note says "beneath the angle of the jaw" while its trigger criterion says "talking". Every one of TN's three suppress-gates is reachable by a GPN patient ticking honestly on a co-tenanted screen. Sibling branches with distinct `fires()` predicates close that path structurally, and they are the established pattern here (`b-occipital`, `b-stabbing`, `b-trigeminal` already run three siblings off one substrate chip). Second, the plan adds two entries to each of five hand-maintained `PhenotypeId` lists, of which only one has a mechanical guard: `CHAPTER_ORDER` is module-private, typed `readonly string[]` rather than `readonly PhenotypeId[]`, silently falls back to `CHAPTER_ORDER.length` on a miss, and has no test; the `MANAGED`/`switch` pair has no invariant; and the `HiddenClaimMarkers` span list is eighteen hardcoded literals whose omission is a clinical-reviewer block that no hook can catch. This batch is precisely the wrong time to leave those unguarded, because item 4 deliberately splits the two new phenotypes across the `MANAGED` boundary. Third, the plan touches well over five files and extends two shared unions with no rollback note, and the `TASKS.md` entry is a scope sketch missing every §15 field. On the four questions put to me: keep `ichd3-2018` as one record (splitting multiplies `last_reviewed` dates without reducing verification work); PIFP criteria-only is structurally sound because the existing `showLeadingGapNote` predicate was built and tested for exactly this case last batch and criteria D/E carry the workup message on the criteria surface without new authored prose; chip reuse is safe for severity, quality, and chronicity and must be a mint for GPN's duration window and trigger and PIFP's daily-over-two-hours criterion; and sibling branches, not a shared screen. None of this reaches the block bar. The rubric-6 trigger technically fires on file count plus shared abstraction with no rollback note, but the change is purely additive with no rename, no schema change, and no persisted state (the pathway holds all answers in component-local `useState`), so the revert is one command, and my predecessor treated an aggravated version of the same fact pattern as a merge condition rather than a block. I apply that precedent deliberately rather than by default.

## Rubric scoring

1. **Duplication risk — concern.** No parallel implementation; every change extends a structure that exists. The concern is degree, not kind: the same `PhenotypeId` list is now maintained by hand in five places (`HEADACHE_PHENOTYPES`, `CHAPTER_ORDER`, `MANAGED` + its `switch`, the reachability `WALKED`/`UNWALKED_DEBT` partition, the `HiddenClaimMarkers` spans) and this plan grows all five. Separately, encoding "not better accounted for by another ICHD-3 diagnosis" as a criterion (plan item 2) would introduce a criterion kind that none of the sixteen existing phenotypes has.
2. **Boundary integrity — pass.** Nothing crosses. ICHD-3 criteria and gate roles in the engine, `fires()` and answer-to-chip mapping in the question config, dosing prose in the management component, verbatim source text in the registry, claim bindings in `claims.ts` with a `data-claim` attribute at the JSX surface. The one boundary watch item is the "not better accounted for" criterion, which would put clinician judgment into a layer that has no chip-answerable substrate for it; see condition 6.
3. **Composability — concern.** The engine is bespoke to one surface by design and documented as such, which is intentional and fine. The miss is that the plan solves a five-list synchronisation problem with five more hand edits and no note. Two of the three fixes are a single test each; the third (`HiddenClaimMarkers`) can be converted from a reviewer-memory problem into a compile error.
4. **State locality — pass.** Zero state added at any scope. `answers: Record<string, string[]>` in `ClinicHeadachePathwayV4` is already generic over question ids, so new branches need no state change, and the progress counter already reads `activeQuestions.length` so a growing branch set is handled.
5. **Dependency weight — pass.** No new package. Everything uses the installed `vitest`, the existing chip/criterion vocabulary, and existing Tailwind tokens.
6. **Migration exit — concern.** Well over five files, and two shared unions (`ChipId`, `PhenotypeId`) grow. No rollback note in the plan and no `Rollback plan` line in the `TASKS.md` entry, which is the literal rubric-6 block trigger. It does not meet the block bar in substance: the change is additive, nothing is renamed, no data schema moves, and the pathway persists nothing, so `git revert` is complete and sufficient. One edit is *not* purely additive and must be named: a new option on `q-location` changes an existing single-select core screen, so an angle-of-jaw presentation that previously answered "in the face: cheek, jaw, or upper lip" will now be steered elsewhere, changing the chip set and therefore the differential for a presentation that exists today.

## Rulings on the questions raised

**(a) Chip reuse vs new chips.** The governing rule, which should be written once as a comment above the `ChipId` union so it is not re-litigated a fourth time: **reuse a chip only when the chip's label, which is the thing the clinician actually affirms, is logically equivalent to the criterion's requirement.** A label wider than the criterion manufactures false positives; a label narrower than the criterion manufactures false negatives, which is the `sev-very-severe` defect exactly. Applying it:

- **Severity — reuse.** GPN B.2 "severe intensity" is satisfied by either severity answer; use the `sev-severe || sev-very-severe` disjunction exactly as `tn-B` and `on-B` do. `q-severity` is single-select and TN-class pains are routinely reported as very severe; anything narrower reproduces U1.
- **Quality — reuse.** GPN B.3 "electrical, shooting, stabbing or sharp" is co-extensive with TN B.3; use the `qual-electric-shock-shooting || qual-sharp-stabbing` disjunction counted once, per the `on-B` idiom.
- **Chronicity — reuse.** PIFP's ">3 months" maps to `pattern-ge-3-months`, which is the same approximation already accepted for `cm-A`, `hypnic-C`, and `ndph-A`. Consistent; do not mint a near-duplicate.
- **Duration — mint.** The engine's actual convention is one duration chip per criterion window: `dur-lt-15-min`, `dur-15-to-180-min`, `dur-2-to-30-min`, `dur-1-to-600-sec`, `dur-seconds-to-minutes`, `dur-fraction-sec-to-2min`, `dur-15min-to-4h`, `dur-30min-to-7days` already coexist with overlapping ranges. Minting is the pattern, not the exception. Specifically, `dur-seconds-to-minutes` (occipital, "a few seconds to minutes") is *wider* at the upper bound than GPN's two-minute cap, so reuse would admit patients the criterion excludes; `dur-fraction-sec-to-2min` (TN) is wider at the lower bound. Mint.
- **GPN trigger — mint.** "Swallowing, coughing, talking or yawning" is a different trigger set from `trigger-innocuous-stimulus`. Mint, and do not let the new chip feed `tn-C`.
- **PIFP frequency/duration — mint, and specifically do not route it through `dur-continuous`.** `freq-ge-1-per-day` is an attack-count chip living in the TAC-detail group and does not mean "daily for more than two hours". `dur-continuous` is in the `episodicPhenotypes` continuous-suppression list inside `evaluateHeadachePhenotypes`, so reusing it would silently drop migraine, TTH, cluster, PH, and SUNCT from a facial-pain patient's differential. Mint a PIFP-specific chip.

**(b) One branch or siblings — siblings.** The repo contains both patterns, and the discriminator is principled: a screen may be shared when the two phenotypes have the *same* `fires()` predicate (`q-tac-detail` legitimately serves paroxysmal hemicrania and SUNCT/SUNA, which differ only by a duration window under one trigger condition); sibling branches are correct when the predicates differ (`b-occipital`, `b-stabbing`, `b-trigeminal` are three siblings off `qual-sharp-stabbing`). GPN's substrate is throat/tongue-base/ear territory with a swallow trigger; PIFP's substrate is facial location with a *dull* quality, the opposite of TN's; `b-trigeminal` already fires on shock-or-sharp quality **or** `loc-facial-region`. Three different predicates, therefore two new sibling branches: `b-glossopharyngeal` and `b-pifp`, each with its own conditional prompt in the established "If this is X, answer these" idiom. Do not widen `b-trigeminal`'s `fires()` and do not add GPN or PIFP options to `q-trigeminal`. Beyond fitting the pattern, this is the structural fix for the false-positive path described in condition 4: a throat-territory patient never sees the TN options at all.

**(c) PIFP criteria-only — acceptable as planned, with one test.** `showLeadingGapNote(top2, manageable)` already gates on `manageable.length > 0`, so it can never point at an absent block; it already excludes vestibular migraine; and it was given two invariants tests last batch. PIFP leading with a manageable runner-up exercises that tested path and adds no new display state. I considered requiring a workup-note row instead, on the NDPH precedent (a phenotype with no drug protocol that nonetheless carries a card), and rejected it: PIFP's mandatory-workup message is criteria D and E themselves ("clinical neurological examination is normal", "a dental cause has been excluded by appropriate investigations"), which render in the row's criteria list from verbatim ICHD-3 text with no newly authored prose and no source the repo does not hold. That is the cheaper and better-sourced surface. Add the PIFP-leads case to `headacheResultV4.invariants.test.tsx` and open a `TASKS.md` entry for a PIFP workup card should a source ever be held.

**(d) `ichd3-2018` — keep one record, do not split.** It is one publication with one PMID, one year, one edition, and one review window; N per-chapter records would carry the same PMID and N `last_reviewed` dates that must move together, which is N ways for them to drift apart and no new information. Section granularity already lives at the layer where it actually varies: each claim's `citation_ids` plus its own `description` names its section, and the record's `section` field carries the list. Splitting would re-point roughly twenty-five claim entries for zero functional gain, which is a high-cost, low-benefit migration under rubric 6. The honest counterweight is that §13.6 step 3 requires re-verifying every dependent claim on each refresh, and that set has grown from the twelve the record's comment still names to roughly twenty-four; splitting does not reduce that work, it only shards it. If the record's `quoted_text` ever does need restructuring, the shape to prefer is `quoted_sections: Record<string, string>` keyed by ICHD section on the *same* record, which keeps one PMID and one `last_reviewed` while making per-section retrieval possible. Not now.

**(e) Sync points.** Three guards ship with this batch (condition 7). `CHAPTER_ORDER` is the most urgent: private, typed `readonly string[]` so a typo type-checks, silent `CHAPTER_ORDER.length` fallback on a miss, and no test, which means omitting a new id produces a silent tie-break ordering defect rather than a failure. `MANAGED` and its `switch` are hand-synced and this plan deliberately puts one new phenotype on each side of that boundary. The `HiddenClaimMarkers` list is eighteen hardcoded spans whose omission is a clinical block that no hook catches; a typed `Record<PhenotypeId, string | null>` rendered by `Object.entries(...).map(...)` converts that entire class into a compile error, which is strictly better than a test. Two items need no action: the dev-time suppression-path invariant and the `SUBTYPE_RESOLVERS` key invariant already iterate `HEADACHE_PHENOTYPES` and are exhaustive by construction. Two need a stated decision rather than a guard: neither new phenotype belongs in `episodicPhenotypes` (TN and ON are not there either, and PIFP is a daily entity that would suppress itself), and neither belongs in `EMIT_CRITERION_IDS` (both should DROP silently on substrate absence, like TN and ON).

**(f) Other structural items.** No new ADR: ADR-2026-07-06 governs, the §4.7, §4.9, §13.1, and §13.4 phenotypes were all added under it without one, and nothing here changes the shape of the chip, criterion, branch, banding, subtype, or management layers. The one genuinely ADR-shaped item is the chip-reuse rule, which is better placed as a comment above the `ChipId` union than as a document. No `@seo-specialist` sign-off is required: the route and its manifest metadata are untouched, and in-pathway criteria and interpretation strings are explicitly outside that reviewer's trigger per §11. Gate 6 is structurally weak for this batch and should be described honestly rather than reported as a pass that means more than it does: the result surface sits behind an interactive flow (safety screen, then questions), so a static fetch of `/pathways/headache-clinic` can confirm only that the page returns 200 and the safety screen renders. The real verification for this change is the reachability walks, which is the point of that harness.

## Required follow-ups

3. **Give GPN a real `q-location` answer, not just a branch option.** A branch option reachable only through the quality screen reproduces the exact unreachability defect fixed on 2026-09-07 (facial pain had no location answer, so TN was undiagnosable). 4. **Add the cross-phenotype false-positive walk.** Assert that a glossopharyngeal presentation does **not** produce a `full` trigeminal-neuralgia match.
