## Rationale

This is a defect batch, not a design, and it behaves like one: no new module, no new abstraction, no new dependency, no new state. Every fix lands in the joint the existing architecture already provides — a routing defect becomes a widened `fires` predicate, an unreachable criterion becomes an answer option that contributes the chip nobody was contributing, a mis-resolved subtype becomes one more ternary arm in `SUBTYPE_RESOLVERS`, and two new management surfaces become two more `case` arms behind the same `hasHeadacheManagement` predicate. The engine/config/display layering set by ADR-2026-07-06 and the v4 rebuild review is respected throughout, and the one place the batch could have cheated (the newly authored TN and occipital cards, which break the "byte-for-byte relocation" contract in `HeadacheManagement.tsx`) amends the contract in the header comment and points at its own clinical gate rather than quietly violating it. That is the correct handling. The reachability harness is the highest-value artifact here: it converts an entire class of silent defect (criteria that evaluate correctly but that no answer path can produce) into a test failure, and it found the orphaned cluster criterion on its first run. The risks are all small and all of the same kind — hand-synced pairs that no longer have a mechanical guard: two now-identical `fires` predicates that must widen together or cluster silently caps at Probable again; a `MANAGED: Set<string>` hand-synced with a `switch(phenotypeId)`; a `WALKED`/`UNWALKED_DEBT` partition maintained by hand inside the test; and a three-clause display predicate whose semantics live entirely in a comment. None of these is a rubric block; each is one line of tightening. Two things do have to be fixed before merge: the batch touches a shared primitive with seven consumers and changes visible behavior on three pathways outside headache, which has to be stated and live-verified; and the reachability test cites a `TASKS.md` debt entry that does not exist. Separately, and outside the scope of this batch, the mandatory safety strip on this very page links to a route that is not registered.

## Rubric scoring

1. **Duplication risk — concern.** No parallel implementation and no new infrastructure; every change extends a structure that already exists. Two sub-issues: (a) `b-cluster-detail` and `b-cluster-subtype` now carry byte-identical `fires` predicates, and this file already has the extraction idiom for exactly this (`anyAutonomic`, `migraineSuggestive`); the divergence failure mode is the defect this batch just fixed. (b) The BC-7 vascular-mimic caution now exists as prose in two places — `sym-reversible-neuro-reported.teachWhenSelected` (aura group) and the new `q-aura.teach` — of which only the second renders (see follow-up 4). Duplicated clinical prose with one live copy is a drift hazard.
2. **Boundary integrity — pass.** Nothing crossed. ICHD-3 criteria and subtype precedence stayed in `clinicHeadacheData.ts`; routing stayed in `headacheQuestions.ts`; management prose stayed in `HeadacheManagement.tsx`; the three new claims are registered in `src/lib/citations/claims.ts` with `data-claim` attributes at the JSX surface, and both cited citation ids resolve in `registry.ts`; page metadata stayed in `routeManifest.ts`. The amber note is display policy about which management block is showing, which is `HeadacheResultV4`'s own concern — correct layer, wrong shape (item 3).
3. **Composability — concern.** The amber-note gate is a three-clause inline predicate carrying band semantics documented in a 13-line comment, sitting next to an invariants test file that is the natural home for the test it currently cannot have. `'vestibular-migraine'` is a bare string literal in multiple places in that file. Separately `MANAGED` is typed `Set<string>`, not `Set<PhenotypeId>`, and is hand-synced with the `switch(phenotypeId)` below it — now 12 entries against 16 phenotypes.
4. **State locality — pass.** Zero state added at any scope. The progress change reads `safeIndex` and `activeQuestions.length`, both already derived in `ClinicHeadachePathwayV4`, and moves the display closer to the live sequence rather than further from it. Nothing is hoisted.
5. **Dependency weight — pass.** No new package. The harness uses the installed `vitest`; the amber note uses existing Tailwind tokens; no new icon import.
6. **Migration exit — concern.** Nine files, and one of them (`PathwayHeader.tsx`) is a shared primitive with seven consumers whose visible behavior changes on three pathways outside headache (`StatusEpilepticusPathway`, `ExtendedIVTPathway`, `PostStrokeLipidManagement` all pass a `CopyState`; `EvtPathway`, `MigrainePathway`, `PearlDetailView` pass boolean or nothing and are unaffected). The revert itself is genuinely cheap — no schema change, no rename of a shared abstraction, no data migration, one `git revert` — so this does not meet the block bar, but §16 requires the rollback note and the cross-pathway blast radius has to be stated rather than discovered.

## Rulings on the eight structural questions raised

1. **Shared `fires()` predicate — extract it.** The cluster pair is one clinical concept ("the cluster attack picture") deliberately split into two screens by clinical review BC-9, and they must fire and stop firing together forever. A future author widening one and not the other reproduces the exact defect this batch fixes. Extract to a named local helper beside `anyAutonomic`/`migraineSuggestive`. Condition 2.
2. **One-option single-select `q-cluster-detail` — acceptable as-is, do not add a second option.** The engine treats unanswered as not-contributing, and every screen already carries "Skip (unsure)", which is the established negative exit. A "does not fit" option would either contribute no chip (a novel data shape) or need a negation chip the engine has no concept of. Neither earns its keep. Whether a lone commit-and-advance radio card reads well at 375px is a UI call; route to `ui-architect` + `mobile-first-developer` if V wants it revisited.
3. **Contradictory-state guard in the resolver — right layer.** Single-select is a UI constraint, not a data invariant; `selected` is derived from `answers`, and the repo already persists interview drafts elsewhere (`src/lib/nihssDraft.ts`), so "restored or merged state" is a real future input. The resolver is the only layer that sees both chips, and putting ICHD-3 precedence in the page reducer would be the boundary violation. Returning `undefined` is consistent with ADR-2026-07-06 condition 3 (the resolver never suppresses the parent). Only §3.1.1/.2 is a definitionally exclusive pair with a wrong silent default. Targeted guard, not a generic mechanism. Approve as written.
4. **Routing flags in `HEADACHE_CHIP_GROUPS` — correct placement, and the premise behind the question is wrong.** `HEADACHE_CHIP_GROUPS` is not test-only: it is the runtime chip registry backing `getChip()`, which is read by `deriveHeadacheConflict` and by `contributingChipLabels`, both of which render. More decisively, the drift guard mandated by the v4 rebuild review (`headacheQuestions.test.ts`, "every chip referenced by any answer option resolves via `getChip()`") makes registration in `HEADACHE_CHIP_GROUPS` *mandatory* for any chip an answer option contributes. A separate `ROUTING_FLAG_CHIPS` home would break that guard for zero benefit. The flags are safely inert in the render paths that matter: `getChip` is only reached from a criterion's `contributingChips`, and these belong to no criterion. The `ROUTING FLAG` comments are the right lightweight marker. One real sub-issue about dead surface — follow-up 4.
5. **Hand-maintained `WALKED`/`UNWALKED_DEBT` — acceptable debt shape, tighten later.** The guard fails when a phenotype is added and accounted for nowhere, when a listed id no longer exists, and when an id is double-listed. That is a real wall, and a strict improvement on the previous guard whose loop body never executed. The clean derivation is a `WALKS: Partial<Record<PhenotypeId, Path>>` table driving `it.each`, after which `WALKED` is `Object.keys(WALKS)` and cannot drift. Recommend, do not require.
6. **Amber-note predicate — extract and test it.** The logic is right, including the two non-obvious calls (suppressing on VM because VM legitimately steers to the migraine block, and gating on `manageable.length` so the note can never point at an absent block). But correctness that lives only in a comment survives exactly one careless edit, and the inline form cannot be tested. Hoist to a named `const`, promote `'vestibular-migraine'` to a module constant, add invariants tests. Condition 3.
7. **ADR — confirmed, no ADR.** There is no decision here to record: the chip/branch/criterion engine, the post-evaluation resolver pass, the banding layer, the claim-tagging surfaces, and the management-block pattern are all unchanged in shape; the `ChipId` union grows additively, a thirteenth conditional branch joins twelve, a resolver body gains a guard within ADR-2026-07-06's stated semantics, and one shared primitive gets a bug fix. §16 attaches ADRs to Class D structural decisions, not to defect batches inside a decided architecture. What must exist instead: the §16 rollback note (condition 1), the missing `TASKS.md` debt entry (condition 5), and the `### @seo-specialist — Sign-off` block for the indexable-route metadata change (condition 7).
8. **Blast radius.** To the ED headache pathway: **zero**. `HeadacheWorkup` (route `/guide/headache-workup`) consumes neither `PathwayHeader` nor the clinic engine. The real radius is elsewhere and is understated in the batch — see conditions 1 and 4, and the two out-of-scope observations below.
