## Rationale

**Rubric scoring**

| # | Item | Score | One-line rationale |
|---|---|---|---|
| 1 | Duplication risk | concern | Reuse of the existing fetchers is right, but three parallel implementations are unaddressed: the `indexation-check.mjs` port duplicates `scripts/seo/fetch-gsc-inspections.mjs`; `site-pages.ts` re-derives titles that `src/seo/routeMeta.ts` already owns; `seo:weekly` is kept runnable with no retirement trigger. |
| 2 | Boundary integrity | concern | Write allowlist and the `scripts/` → `src/` import direction are both correct, but no layer of the report-only stack is hook tier, and "report-only" is file-scoped while the job performs unattended *external* writes (sitemap submit, indexing requests) on an already-granted write scope. |
| 3 | Composability | concern | `config.mjs` is a genuine extraction, but three residues keep site three from being a config file: a second config source in `lib/google-auth.mjs`, the dashboard URL living in the procedure file, and a NeuroWiki-specific `kind` union baked into the shared `PageRecord`. |
| 4 | State locality | pass | Ledgers sit next to their consumers under `docs/seo/`; run state is per-date under `docs/seo/runs/`; nothing is hoisted to a scope wider than its readers. Only `pages-snapshot.json` is misfiled (derived output in the raw-capture directory). |
| 5 | Dependency weight | pass | No new package is required. `googleapis`, `@google-analytics/data`, `google-auth-library`, `tsx`, `puppeteer`, and `jsdom` are all already in `package.json`. |
| 6 | Migration exit | concern | A rollback note exists, which satisfies the Class D requirement, but the blast radius is well past five files and half the revert (the scheduler wrapper) lives outside git, so a partial rollback leaves an unattended job pointed at a deleted procedure. |

**The call.** This is a well-shaped plan and the strongest part of it is the part that is easiest to get wrong: it correctly identifies that NeuroWiki already owns the data layer and Tidbit owns the judgment layer, it accounts for all 26 scripts in `/Users/vaibhav/Documents/Tidbit Health/Tidbit-Website/scripts/seo/` with an explicit fate for each, and it chooses a write allowlist (`docs/seo/**`, `docs/seo-data/**`) that puts every path in `.claude/rules/clinical-surfaces.md` out of reach by construction rather than by vigilance. Every file path the plan references resolves. Three structural things are not yet true as written. First, the plan asserts that after `config.mjs` "no domain, property ID, URL list, or output path is hardcoded anywhere else," and that is false today for the scripts it keeps: `scripts/seo/lib/google-auth.mjs:97` hardcodes `'https://neurowiki.ai/'` as the GSC default and `getSeoConfig()` *throws* when `GA4_PROPERTY_ID` is unset, which directly contradicts `config.mjs` defaulting the property to `'367909578'` and contradicts the claim that a missing `.env.local` no longer kills the run (the `seo:fetch-*` npm scripts invoke `node --env-file=.env.local`, which errors on a missing file). Two config sources with divergent defaults and divergent failure modes is the hidden coupling the config extraction was supposed to remove. Second, the §3 adapter plans to reconstruct each page's current title and description from `routeManifest.ts` + trial data, but `src/seo/routeMeta.ts` already exports `getRouteMeta(pathname): MetaData` — the single function that produces the exact strings the site renders, including trial and `/trials/q/*` question pages — and `src/seo/sitemapRoutes.ts` already exports `SITEMAP_ROUTES` as the canonical path universe; re-deriving both means the job's "old wording" baseline can drift from what is actually served, and a snippet-rewrite proposal against a phantom baseline is the worst output this job can produce. Calling the existing function instead also shrinks the adapter well below the estimated 150 lines. Third, and most important for an unattended job: per CLAUDE.md §2 only hooks are a global tier, and all three of the claimed report-only layers are below it. The governance file is convention, the scoped `git add` is an instruction in a markdown procedure (the Tidbit precedent at `.claude/commands/seo-daily.md:127` confirms the commit is agent-driven, not script-driven), and `clinical-guard.mjs` is only as strong as the agent's willingness to invoke it. One line in `.husky/pre-commit` that rejects a `docs(seo): daily report` commit whose staged paths escape the allowlist converts the strongest layer from convention tier to hook tier, and that single change is the difference between a wall and a promise. None of these is a blocking defect — each is a named, cheap fix — so this approves with the conditions below, all of which should land inside the plan before implementation step 1 rather than being deferred to review of the finished port.

## Required follow-ups

1. **Wire the guard into the hook.** Add a check in `.husky/pre-commit` that fails any commit whose message matches the job's format if staged paths fall outside `docs/seo/**` and `docs/seo-data/**`. Keep `clinical-guard.mjs` as the in-run early warning, but state plainly in the ADR that the hook is the enforcing layer and the other two are convention tier per §2. Note that `--no-verify` cannot be prevented by any local mechanism; the honest mitigation is that the briefing and the run manifest must record the commit SHA and the exact committed paths every morning.
2. **Give the guard a run-start baseline.** Snapshot `git status --porcelain` at run start and compare the delta at commit time. As specified, a strict working-tree check cannot distinguish "the job wrote this" from "V left work uncommitted overnight," so it will either hard-fail most mornings or get loosened until it means nothing.
3. **Adapter must consume, not re-derive.** `scripts/seo/lib/site-pages.ts` calls `getRouteMeta()` from `src/seo/routeMeta.ts` for every `title`/`description` and takes its path universe from `SITEMAP_ROUTES` in `src/seo/sitemapRoutes.ts`, using `public/sitemap.xml` only for `lastmod` and `inSitemap`. The `scripts/` → `src/` tsx import direction is sound and precedented by `scripts/gen-trial-card-meta.ts`, which imports `../src/data/trialData` and runs in `prebuild`.
4. **Collapse the config to one source.** Either have `getSeoConfig()` in `scripts/seo/lib/google-auth.mjs` read from `config.mjs`, or have `daily-run.sh` export the config values into the environment before invoking the kept fetchers. Pick one and write it into §2. Resolve the `--env-file=.env.local` behavior explicitly (invoke the fetchers directly with `node`, or move to `--env-file-if-exists`), because the plan's tolerance claim is not true through the current npm scripts.
5. **Do not port `indexation-check.mjs` whole.** `scripts/seo/fetch-gsc-inspections.mjs` already reads `public/sitemap.xml`, loops URL Inspection at 175 ms (~5.7 req/s), and writes `docs/seo-data/gsc/inspections/<date>.json`. Keep it and port only Tidbit's bucketing and report layer on top, exactly as the plan already does for `fetch-gsc`/`fetch-ga4`. This also corrects the §4 runtime estimate: the existing script budgets ~30 s for 165 URLs, not ~10 min.
6. **Normalize host once, in one place.** `public/sitemap.xml` emits `https://www.neurowiki.ai/...` while the GSC property, `scripts/live-verify.mjs`, and the plan's `baseUrl` are apex. `scripts/prerender.mjs:104-106` already has the canonical normalizer (`/^https?:\/\/(?:www\.)?neurowiki\.ai/i` → path). Reuse that shape, join `PageRecord` on **path** rather than absolute URL, and note that `fetch-gsc-inspections.mjs` currently inspects www URLs against an apex `siteUrl`, so today's inspections snapshot may be empty or erroring — verify that during implementation step 1, not later.
7. **Move the dashboard URL into `config.mjs`.** Hardcoding it in the procedure file recreates risk #6 for the next site by copy-paste. Add `dashboardArtifactUrl` to `SITE`, keep the ban on Tidbit's URL by ID in the governance file, and derive the dashboard title from `SITE.name`.
8. **Make `PageRecord.kind` an opaque string.** Supply the path-to-kind classifier per site in `config.mjs`. Analysis scripts may group and sort by `kind` but must not branch on NeuroWiki's specific member names, or every consumer inherits this site's taxonomy.
9. **Name an end state for `seo:weekly`.** The ADR supersession line is the minimum acceptable disposition, but add the trigger the plan already implies: at three consecutive clean mornings, either delete `generate-weekly-report.mjs` and `audit.mjs` or rename the script `seo:weekly:legacy` with a console banner pointing at the daily briefing. Two report generators reading the same snapshots with no retirement date is how the third pattern gets born.
10. **State the external-write allowlist.** "Report-only" is true for repo files but not for external state: `SCOPES` in `scripts/seo/lib/google-auth.mjs:25` includes write-scoped `webmasters`, and the plan schedules unattended sitemap submission plus two indexing requests per morning. Enumerate the permitted outbound write calls in `.claude/rules/seo-daily-governance.md` the same way paths are enumerated, and declare every other API call read-only.
11. **Fail closed on rollback.** The scheduler at `~/.claude/scheduled-tasks/neurowiki-seo-daily/` is outside git, so a revert of the port cannot remove it. Require the wrapper to abort if `.claude/commands/seo-daily.md` or the governance rule file is absent, and land the port as a single revertable commit (or record the exact commit range in the ADR), so the rollback note in §12 is executable rather than aspirational.
12. **Anchor the new rule file to its tier.** `.claude/rules/seo-daily-governance.md` only sits at CLAUDE.md tier if CLAUDE.md @-references it, as it does for `clinical-surfaces.md` and `clinical-review-templates.md`. Add that reference in the same commit as the §16 scope-list and §22 command-table amendments. Also add the `Co-Authored-By:` trailer to the job's commit template so the §16 format is compliant from day one.
13. **Relocate `pages-snapshot.json`.** It is derived from committed source and will churn a diff every run inside a directory that otherwise holds captured external data. Put it under `docs/seo/runs/<date>/` or gitignore it; do not mix derived and captured artifacts in `docs/seo-data/`.
14. **Route the clinical clauses of the governance file to `clinical-reviewer` for a one-time read** before implementation step 6. The port itself is correctly classified as not `-clinical` — the job cannot write any clinical surface — but §8.3 defines when a drafted proposal escalates to the Class E path, and that boundary is clinical-reviewer's to ratify, not mine. Worth stating in the ADR: `check:humanizer` scans `src/pages`, `src/components`, `src/data`, `src/seo`, `src/config`, `src/lib/cases` and therefore does **not** scan `docs/seo/proposals/`, so the humanizer rule is convention tier while a proposal is a draft and hook tier the moment V applies wording into `src/config/routeManifest.ts`. That is the right split; it should be written down rather than assumed.
